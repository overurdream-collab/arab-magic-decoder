## 1. المهمة والحدود

منصة سوق يمني متعدد التجار لقطع غيار السيارات، بكتالوج مركزي وارتباط قطع بالمركبات، وعروض التجار والأسعار والمخزون، وطلبات المشترين، مع توسع مستهدف إلى التوصيل والورش والخدمات والدفع والتحليلات ووكلاء الذكاء الاصطناعي والتطبيقات الأصلية.

- **تعليمات المالك:** الاستمرار في التطوير والاختبار دون انتظار موافقة لكل تغيير اعتيادي، لكن لا تنفيذ تغييرات إنتاجية خطرة، ولا دفع حقيقي، ولا نشر إنتاجي أو حذف بيانات دون تفويض واضح.
- لا تمس مشاريع أخرى؛ لا تعيد بناء أجزاء مستقرة بلا مبرر؛ لا تضف بيانات تجريبية إلى الإنتاج؛ لا تخزن أسرارًا في Git.
- اعمل بفروع صغيرة وPR وفحوص CI قبل الدمج؛ migrations تقدمية قابلة للمراجعة؛ تحقق من RLS والتفويض على الخادم، وليس في الواجهة فقط.
- افصل **طلب توافر/شراء غير مدفوع** عن **طلب مدفوع أو مكتمل التوصيل**. لا تساوِ `fulfilled` بتأكيد استلام العميل أو تحصيل نقدي.

## 2. التقنية الموجودة فعلاً

- **واجهة الويب:** React 19، TypeScript، TanStack Start/Router، Tailwind CSS، العربية RTL، Vite.
- **البيانات والمصادقة:** Supabase / PostgreSQL، أدوار وRow Level Security، دوال SQL RPC.
- **إدارة الحزم:** ملف `bun.lock` عند وجوده؛ CI يستخدم `bun install --frozen-lockfile`. راجع `package.json`؛ `npm run dev`, `npm run build`, `npm run lint`.
- **بيئة اختبار:** GitHub Actions، PostgreSQL 16 منفصل واختبارات SQL، Supabase محلي مع حسابات اصطناعية، Playwright Chromium.
- **غير موجود في هذا المستودع كمنتج مكتمل:** Laravel/Active eCommerce، أربع تطبيقات Flutter، محرك تسوية مالية، بوابات دفع حقيقية، منظومة وكلاء AI منتجة.
- `README.md` لا يزال وصفاً عاماً قديماً؛ هذه الوثيقة و`docs/PROJECT_BASELINE.md` أوثق لتحديد نطاق قِطَع.

## 5. عقد طلب الشراء الحالي — لا تكسره

المشتري يطلب قطعة من عرض تاجر بكمية ضمن الحدود؛ الطلب الأولي لا يحجز مخزوناً. قبول التاجر يحجز الكمية مع قفل صفوف المخزون؛ الرفض لا يحجز؛ الإلغاء المسموح بعد القبول يعيد المخزون؛ إتمام التاجر يغلق الطلب دون إعادة المخزون. توجد حدود للكمية ومنع تكرار الطلب المفتوح، مع فصل صلاحيات المشتري والتاجر.

- تحقق من المصدر الحقيقي في `supabase/migrations/20261014040000_purchase_requests.sql` وترحيلات الأذونات/منع التكرار في `20261015000000_...` و`20261015020000_...`.
- دوال RPC ذات الصلة: `create_purchase_request` و`seller_respond_to_request` و`buyer_cancel_request` و`list_my_purchase_requests` و`list_seller_purchase_requests`.
- لا تسمح لعميل مباشر بكتابة حقول الحالة/الكمية/السعر عبر الجدول؛ استخدم RPC مع تحقق دور وملكية وتدقيق.
- لا تعتبر المخزون المتاح، الحجز، إتمام التاجر، التسليم، والتحصيل المالي شيئاً واحداً. افصلها بعقود حالة واضحة قبل توسيع الإنتاج.

## 6. الفحوص وكيفية التحقق

1. استنسخ المستودع وافحص `git status` و`git rev-parse HEAD`؛ لا تبدأ من فرع محلي متأخر.
2. نفذ `bun install --frozen-lockfile` ثم `bun run lint` و`bun run build` وفق إصدار Bun المستخدم في CI.
3. افحص `.github/workflows/qitaa-db-ci.yml`؛ يشغّل `tests/db/bootstrap.sql` واختبارات الأمن والطلبات في PostgreSQL منفصل.
4. افحص `.github/workflows/qitaa-buyer-seller-e2e.yml`؛ ينشئ Supabase محلياً ويختبر رحلة متصفح بأسماء حسابات اصطناعية.
5. راجع جميع الفحوص الخمسة: Qitaa CI، Qitaa DB Security، Qitaa HTTP Smoke، Qitaa Vehicle Reference Preview، Qitaa Buyer-Seller Browser E2E.
6. **مهم:** كانت مجموعة تزامن المتصفح عامة فتُلغي اختبارات PR مختلفة. أصلح PR #19 ذلك على `main`؛ عند إعادة تشغيل اختبارات فروع قديمة راجع إصدار workflow المستخدم وسلوك الإلغاء.
7. لا تدمج PR بفحص فاشل أو ملغى أو معلق دون تحقيق سبب الفشل. تحقق من أحدث SHA قبل الدمج لتجنب دمج تغييرات متزامنة.

## 7. ما لم يُثبت إنتاجياً

- لا توجد شهادة جاهزية إطلاق، ولا قبول مستخدمين حقيقيين لرحلة الشراء/التاجر/التوصيل/الدفع.

- البيانات التجريبية لملاءمة القطع ليست إثباتاً هندسياً موثقاً؛ لا تضع شارة «متوافق مؤكداً» دون مصدر موثوق وتتبّع.

- لا ترفع أو تهاجر بيانات مستخدمين حقيقية في اختبارات GitHub؛ لا تستخدم بيانات الاعتماد الإنتاجية.
- مراجع أرقام الجداول في سجلات أكتوبر لقطات قديمة؛ ليست قياسات اليوم.
